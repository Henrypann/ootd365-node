# 路线图

Roadmap and boundary map for ootd365-node. 这份文件说「以后做什么、按什么顺序、什么条件才能进下一阶段」。它不是契约：字段和规则仍以各版本的契约和 schema 为准。

## 愿景

被动的晨间穿搭系统，目标体验接近 Oura 或 Whoop：不用手动记录，每天自己有一份读数。

- 早上醒来，收到天气和一套推荐搭配。
- 出门时，门后或镜子旁的摄像头看到你实际穿了什么，节点本机比对，记成事件。
- 你只在它认错时点一下纠正。纠正就是训练数据。

手动登记的衣橱不是绕路，它是这个系统的**底库**（gallery）：摄像头看到的东西，要和你登记过的那几十件比对，才知道是「你的那件藏青 T 恤」，而不是「一件藏青 T 恤」。所以登记照片就是以后的注册样本，刀 1 的 `cos_keys` 不会作废。

## 原则

1. **本地优先。** 主代理、比对、画面都在家里的节点上。云只放私有对象。
2. **先有数据，再有智能。** 每个阶段都能独立用起来，也都留下下一阶段需要的标注数据。
3. **人是最终读数。** 被动识别只提议，人确认或纠正。没确认的事件不改计数。
4. **闸门，不是日期。** 进下一阶段靠可测的条件，不靠时间表。
5. **新能力开新版本。** `wardrobe-v1` 的 schema 保持封闭。加 embedding 之类的字段，开 `wardrobe-v2`，不放宽 v1。

## 阶段

### V0：手动闭环（刀 1 到 3）

目标：没有摄像头，也能每天用起来，并开始积累事件数据。

| 刀 | 内容 | 状态 |
| --- | --- | --- |
| 1 | 私有 COS 对象键、sidecar 衣橱清单、校验脚本与 CI | 完成 |
| 1.5 | 事件契约 `wardrobe-events-v1`：只追加的穿着和洗涤日志，`source` 先只有 `manual`，`confidence` 留给以后的版本 | 完成 |
| 1.5 | 登记与记录：家庭节点（`server/`）+ 手机 app（`app/`）。登记单品和多张照片，每天点选穿了什么，可附镜子照片 | 完成 |
| 2 | 本地晨间代理：按天气、季节、状态、最近穿过的时间，用规则选一套，输出平铺搭配卡（用你自己的单品照片拼成） | 以后 |
| 2 | 晨间通知（先发到手机）与「穿了 / 换一套」一点即记 | 以后 |
| 3 | Pi 5 编排与晨间屏幕 | 以后 |

闸门：连续两周、约 30 件真实单品，你仍然在点「穿了」。做不到就先修体验，不往下走。

### V1：被动识别

目标：出门时自动读出你穿了什么，你只纠错。

- `wardrobe-v2`：新增本机 embedding，只存在节点，不进 git，不进桶。
- 先离线验证：两周镜子自拍，在笔记本上比对，量准确率，再决定要不要做硬件。
- 门后或镜子旁的摄像头，每天出门时抓一次，不是全天监控。
- 比对结果带置信度，低于阈值的不写计数，进「待确认」。
- 事件的 `source` 区分 `manual` 与 `camera`，`camera` 事件需要人确认才计入 `wear_count`。

闸门（建议值，跑完离线实验再定）：在人确认过的日子里，单品级 top-1 命中率达到 85% 左右，且「待确认」每天不超过 2 到 3 件。

### V2：从纠正里学习，出读数

目标：像 Whoop 一样有「分数」，而不只是识别。

- 用纠正记录调整阈值和每件单品的登记照。
- 轮换读数：最近没穿的、穿太多的、该洗的。
- 日历和场合进入推荐。
- 衣橱读数：每件单品的穿着成本、闲置清单、缺口。

### V3：虚拟形象与试穿

目标：「虚拟的你」穿着推荐搭配。

- 放最后。需要 GPU 级模型，和本地优先、不出家门的原则有冲突，进入前要单独决定放在哪里跑。
- 在此之前，平铺搭配卡就是推荐的展示形式。

闸门：V1 与 V2 的循环已经稳定，并且单独决定了身体图像是否允许离开家里的节点。

## 边界地图

### 现在不做，路线图里有

| 能力 | 阶段 | 进入方式 |
| --- | --- | --- |
| 摄像头抓取与自动服装识别 | V1 | 新版本契约，先过离线闸门 |
| embedding 与相似度比对 | V1 | `wardrobe-v2`，本机存放 |
| 识别置信度与待确认 | V1 | 事件契约里的 `source`、`confidence` |
| 按事件计算 `wear_count`、`wash_count` | V1 | 见下文「规则怎么变」 |
| 轮换读数与分数 | V2 | 从事件日志计算，不写回清单 |
| 虚拟形象、试穿 | V3 | 单独决定算力放哪里 |

### 长期不做

这些不是推迟，而是红线。路线图任何阶段都不改。

- 人脸识别、人脸数据、识别「你是谁」。系统比对的是衣服，不是人。
- 保存原始摄像头画面。比对完即删，只留结果和你确认过的登记照。
- 把云端当作主代理，或把画面送到云端做识别。
- 公开读的桶、写进仓库的密钥、真实衣橱照片入库。
- 拍摄家里其他人为目的的功能。摄像头只在你主动设定的出门时段工作，并有可见的开关。
- 把 Pi 5 当作 GPU 来规划。

## 规则怎么变

`wardrobe-v1` 现在写着：`acquired_at`、`season`、`wear_count`、`wash_count` 禁止靠看图推断。被动识别要改的是其中一部分，需要明确写下来：

- `acquired_at`、`season`：**仍然禁止**视觉推断，永远由人填。
- `wear_count`、`wash_count`：V1 起改为**由事件日志计算**。来源是人记录的事件，或人确认过的 `camera` 事件。没确认的识别结果不计入。
- 这个改动只在 `wardrobe-v2` 与事件契约里生效。`wardrobe-v1` 的文字不改。
